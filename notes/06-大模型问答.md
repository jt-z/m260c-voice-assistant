# 06 - 大模型问答（DeepSeek）

## 1. 设计原则：只问答，不下发动作

命令词没匹配上时，把原话交给 DeepSeek，**只把回复念出来**。

```python
# voice_command_demo.py: ask_llm_and_speak()
log_state(f"命令词没匹配上，交给 DeepSeek：{text}", "recognize")
tts_speak_async(LLM_ACK_TEXT)      # 先播"我想想"给反馈，与请求并行
reply = ask(text)                  # 拿回复
tts_speak(reply)                   # 念出来
```

**模型没有任何执行路径**——回复文本只进 TTS，不进 `subprocess`/`eval`/命令分发。
这是刻意的安全边界：让模型能"说话"很容易，让它能"动手"需要先定义动作白名单。

## 2. 接口（[`llm.py`](../llm.py)）

```python
def load_key() -> str      # 取 API key：环境变量 → 项目内 .deepseek_key 文件
def is_stub() -> bool      # 没配 key → 桩模式
def ask(text) -> str       # 问模型，返回"要播报的文本"；失败抛 RuntimeError
```

### 配置

| 常量 | 值 | 说明 |
|---|---|---|
| `MODEL` | `deepseek-v4-flash` | **推理模型**（见第 4 节的坑） |
| `API_URL` | `https://api.deepseek.com/chat/completions` | OpenAI 兼容 |
| `TIMEOUT` | `(5, 60)` | (连接, 读取) 秒；推理模型出字慢，读取给足 |
| `ATTEMPTS` | 2 | 网络抖动重试次数 |
| `MAX_TOKENS` | **2048** | 必须给思维链留余量（关键） |
| `MAX_SPEAK_CHARS` | 120 | 播报长度上限，超出截断加 `……` |

### key 的两种放法（按优先级）

```bash
# 方式 1：环境变量
export DEEPSEEK_API_KEY=sk-xxxx

# 方式 2：项目内文件（已加进 .gitignore）
echo 'sk-xxxx' > /home/kf/dev/voice_operate/.deepseek_key
```

**都没有 → 桩模式**：不请求真模型，只回一句固定话术，方便先把链路跑通。

```
桩模式收到，你说的是<你的原话>
```

一听就知道是桩，但足以验证「识别 → 回答 → 播报」整条链路。

### 反审的 API 细节

```python
payload = {
    "model": MODEL,
    "messages": [
        {"role": "system", "content": SYSTEM_PROMPT},
        {"role": "user",   "content": text},
    ],
    "max_tokens": MAX_TOKENS,
    "stream": False,
}
headers = {"Authorization": "Bearer " + key, "Content-Type": "application/json"}
r = requests.post(API_URL, json=payload, headers=headers, timeout=TIMEOUT)
```

## 3. System prompt：为"被念出来"而写

```python
SYSTEM_PROMPT = (
    "你是一个中文语音助手, 你的回答会被音箱直接念出来, 用户看不到文字。"
    "要求: 口语化、简短, 控制在 60 字以内; 不要用 markdown、不要 emoji、"
    "不要分点列举、不要念出标点或符号的名称; 直接给结论, 不要客套和重复问题。"
)
```

效果实测：

```
Q: 你好，你是谁
A: 我是你的语音助手，可以陪你聊天、回答问题、查信息。有什么想知道的尽管说。   (36 字)

Q: 帮我算一下 23 乘 17 等于多少
A: 二十三乘十七等于三百九十一。        ← 输出中文数字, 念出来自然
```

注意模型有时会主动把数字写成中文（"三百九十一"），这对语音场景正好。

## 4. 最大的坑：推理模型把 max_tokens 吃光了

### 现象

DeepSeek 时好时坏：**简单问题能答，复杂问题就回退到"暂时还处理不了"**。

### 排查

```python
Q: 查询一下中国有多少个省份
[大模型] 第 1 次调用失败(RuntimeError: 模型返回空内容), 重试…
A: 中国有34个省级行政区  (3.8s)
```

第一次调用返回**空内容**。抓原始响应：

```json
{
  "message": {
    "content": "",                                  ← 空
    "reasoning_content": "我们需要回答用户中文问题：..."   ← 思维链全在这
  },
  "finish_reason": "length",                        ← 被截断
  "usage": { "reasoning_tokens": 200 }              ← 200 个 token 全给了思维链
}
```

### 根因

`deepseek-v4-flash` 是**推理模型**：先写 `reasoning_content`（思维链），想完才产出 `content`。
而 `max_tokens` 是**两者之和**。

原来设 `max_tokens=200` → 复杂问题的思维链直接把额度吃光 → 还没开始正式回答就到上限 →
`content` 为空 → 代码判"返回空内容"抛异常 → 回退兜底语。

简单问题思维链短，能剩下额度，所以**时好时坏**。

### 修法

```python
# llm.py
# deepseek-v4-flash 是【推理模型】: 会先花大量 token 写 reasoning_content(思维链),
# 然后才产出 content。max_tokens 是两者之和 —— 设小了思维链就会把额度吃光,
# 导致 content 为空、finish_reason=length。这里必须给足余量。
MAX_TOKENS = 2048
```

同时在报错信息里带上 `finish_reason` 和 `reasoning_tokens`，下次一眼能看出是不是又触顶：

```python
if not reply:
    raise RuntimeError("模型返回空 content(finish_reason=%s, reasoning_tokens=%s) —— "
                       "通常是思维链吃光了 max_tokens, 可调大 llm.MAX_TOKENS")
```

修后实测：之前必失败的 5 个问题 **5/5 成功，0.8~1.1s**。

## 5. 延迟构成（一次完整问答）

以「你好宽宽你可以做什么」为例：

| 环节 | 耗时 | 能否优化 |
|---|---|---|
| 唤醒后录音 | 3s（`--duration`） | 可缩短，但影响识别质量 |
| SenseVoice 定稿 | ~0.15s | — |
| "我想想" 播报 | 1~1.5s | 预热到缓存后 ≈ 播放时长，无法再压 |
| **DeepSeek 请求** | **0.8~2.5s** | 换更快的模型 |
| 回复**合成** | ~2s | 与上一段播放并行（已做） |
| 回复**播放** | **4~5s** | **大头，由回答长度决定** |

**想明显变快，唯一有效的办法是让回答更短** —— 把 system prompt 的字数上限
从 60 收紧到 30 字，播放时间直接减半。

```bash
voice_command_demo.py --no-llm      # 未匹配命令词时直接播"暂时还处理不了"
```
