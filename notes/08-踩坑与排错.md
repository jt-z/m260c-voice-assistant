本篇是全部踩过的坑的汇总，按排查价值排序。**每个坑都写了现象、根因、修法**。

## 一、协议与串口

### 1.1 串口线程莫名静默死亡

**现象**：程序还活着，日志不动了，喊唤醒词毫无反应。

**根因**：`termios.error` **不是 `OSError` 的子类**。
代码用 `except OSError` 捕获，结果异常穿透出去，把读取线程直接打死，且没有任何日志。

```python
# mic_serial.py: open()
except termios.error as e:                 # 单独捕获这个"野"异常
    os.close(fd)                           # ★ 顺手关 fd，防句柄泄漏
    raise SerialTimeoutError("打开串口失败(...): %s" % e) from e
```

上层 `serial_reader` 再用**宽捕获**兜住，失败就重连，绝不退出：

```python
except Exception as e:      # 用宽捕获: termios.error 等不是 OSError 子类
    log(f"[警告] 串口异常({type(e).__name__}: {e}), 重新连接...")
    mic = None
    time.sleep(3)
```

**教训**：任何"后台常驻线程"的顶层都必须宽捕获，否则一个意外异常就让整条链路静默死掉。

### 1.2 写串口报 `BlockingIOError: [Errno 11]`

**根因**：fd 用 `O_NONBLOCK` 打开，写缓冲区满时立刻抛 EAGAIN。

**修法**：`select` 等可写 + 处理 EAGAIN。

```python
_, w, _ = select.select([], [self._fd], [], min(remain, 0.2))
try:
    n = os.write(self._fd, mv)
except BlockingIOError:
    time.sleep(0.01)      # 缓冲区满，稍候重试
```

### 1.3 唤醒事件被固件重发，动作执行多次

**现象**：喊一次唤醒词，"已唤醒"日志刷好几条；配合"打开图片"会连开好几次。

**根因**：固件在一次唤醒后会重发同一个事件。

**修法**：按 `ivw.start_ms` 去重，30 秒窗口。

```python
stamp = tuple(find_values(obj, "start_ms"))
if stamp and stamp in recent_wakes and now - recent_wakes[stamp] < 30:
    log_state("忽略重复唤醒事件(固件重发)", "listen")
    continue
```

### 1.4 声源角度显示"未知"

**根因**：串口拿到的载荷是 `bytes`，且角度嵌套在多层结构里
（`ivw.angle`、`content.info`（里面还是 JSON 字符串）、或顶层 `angle`）。

**修法**：先 `json.loads`，再**递归提取**（`find_angles` / `find_values` / `has_key`）。

### 1.5 端口号会变，不能写死

**根因**：`/dev/ttyACMN` 按插拔顺序分配。

**修法**：`detect_by_usb(prefer=("1a86","55d4"))` 沿 sysfs 找 `idVendor/idProduct`，
确定性匹配 CH9102；失败才退化为"扫端口 + 找握手帧"。

## 二、音频 / TTS

### 2.1 命令第一个字总被切掉 ⭐

**现象**：`打开图片` → `开图片`，`关闭图片` → `闭图片`。

**根因**：唤醒上报 → 启动 `arecord` 之间有 100~300ms 空隙，第一个字落在这里。

**修法**：进程启动就常开录音 + 1.2s 环形预滚，唤醒时先吐预滚再接实时。
详见 03 篇第 1 节。**A/B 验证**：无预滚切 1.6s → `开图片`；有预滚 → `打开图片`。

### 2.2 中文学被念成一串怪音（"tried saver"）

**现象**：偶尔出现 7~8 秒的怪音，听着像英文但听不出是什么。

**根因**：edge-tts 联网偶发失败 → 旧代码退到 `spd-say -l zh` →
**espeak-ng 的中文是拼音+音素硬拼、无声调建模**，音调全散。

实测：读 10 个中文字要 **6.98s**，读 4 个英文词只要 1.61s。

**修法**：合成加超时+重试；**去掉 spd-say 兜底**（宁可没声音也不要 7 秒怪音）。

### 2.3 所有新合成都失败：`ffmpeg 转码失败 rc=183` ⭐⭐

**现象**：缓存的提示音能播，**任何新文本都失败**。

**排查过程**（走了一大圈弯路）：

| 假设 | 结论 |
|---|---|
| edge-tts 网络问题 | 排除，多次合成成功 |
| mp3 数据损坏 | 排除，截断一半 ffmpeg 照样转成功 |
| 并发合成冲突 | 排除，4 线程并发全成功 |
| Qt 环境干扰 | 排除，Qt 进程内子线程合成成功 |
| `LD_LIBRARY_PATH` 污染 | 排除（qt-xcb / conda lib 都试过） |
| conda 里有别的 ffmpeg | 排除，没有 |
| ffmpeg 各类错误场景 | 全部 `rc=1`，没有 183 |

**转折点**：先给错误信息补上 **ffmpeg 的 stderr**，才看到真话：

```
Unknown input format: 'mp3'
Error opening input file .../xxxx.wav.mp3
```

再 `which -a ffmpeg`：

```
/usr/share/trae-cn/resources/app/bin/ffmpeg    ← 真凶
/usr/bin/ffmpeg
```

**Trae IDE 自带一个 ffmpeg 6.1.1，只支持 8 个 demuxer（连 mp3 都没有）**，
而它排在 PATH 第一位，把系统完整版（341 个 demuxer）遮住了。

**修法（两层）**：

```python
# ① tts.py —— 不信任 PATH
def _ffmpeg_exe():
    for p in ("/usr/bin/ffmpeg", "/usr/local/bin/ffmpeg"):
        if os.path.exists(p) and os.access(p, os.X_OK):
            return p
    return "ffmpeg"

def _ffmpeg_env():                       # 防库劫持
    env = dict(os.environ)
    for k in ("LD_LIBRARY_PATH", "LD_PRELOAD"):
        env.pop(k, None)
    return env
```

```bash
# ② ~/.bashrc 末尾 —— 治本
PATH=$(printf '%s' "$PATH" | tr ':' '\n' | grep -vx '/usr/share/trae-cn/resources/app/bin' | paste -sd: -)
export PATH
```

**最大的教训**：**永远保留原始错误输出（stderr）**。
旧代码 `print("ffmpeg 转码失败 rc=%s" % r.returncode)` 把 stderr 吞了，
只能对着 `183` 这个无意义的数字瞎猜，浪费了大量时间。

### 2.4 播报"成功"但没声音

**根因**：`tts.speak()` 返回 `(是否成功, 方式)`，且**合成失败不抛异常**，
而调用方写的是 `tts_speak(reply)` 不接返回值 → 一路判定成功。

**修法**：检查返回值，失败要明确告知并回退。

```python
ok, how = tts_speak(reply)
if not ok:
    log_state(f"回复合成/播放失败({how})，只显示文字没出声", "warn")
    return False
```

**教训**：`(bool, info)` 这种返回约定，不检查就形同虚设。

### 2.5 两段播报串行，白等 2 秒

**根因**：锁的粒度太粗，包住了"合成 + 播放"。

**修法**：锁只包 `_play()`，合成允许并行。实测 4.0s → 3.0s。详见 03 篇第 3 节。

### 2.6 `Device busy`

**根因**：PulseAudio 会独占 ALSA 硬件，直连 `plughw` 报忙。

**修法**：统一走 PulseAudio（`paplay --device=<sink>` / 设置 `PULSE_SOURCE`）。

## 三、语音识别

### 3.1 Vosk 爱吐重复字 / 空结果

**现象**：`开开开图片`，或者啥也没识别出来。

**修法**：换 SenseVoice（`--asr sv`，默认）。`--asr vosk` 保留作轻量回退。

### 3.2 模型被加载两次（启动慢一倍）

**根因**：`--ui` 模式下 `_ensure_qt_libs()` 可能 `os.execve` 重启自身，
如果它排在模型加载**之后**，模型就会被加载两次。

**修法**：把 `_ensure_qt_libs()` 提到所有模型加载之前。

```python
if a.ui and not a.wav:
    _ensure_qt_libs()          # 必须在加载模型之前
if a.asr == "sv":
    加载 SenseVoice
```

## 四、界面

### 4.1 `could not connect to display :0`

**根因**：无 `DISPLAY`（纯字符终端/ssh 未 -X）或有 `DISPLAY` 但缺 `XAUTHORITY`。

**修法**：`_ensure_x_display()` 自动补 `/run/user/<uid>/gdm/Xauthority`，缺 X socket 时明确报错。

### 4.2 Qt6 xcb 插件缺 `libxcb-cursor.so.0`

**修法**：`_ensure_xcb_cursor()` 用本地兜底目录 + `os.execve` 重启（`LD_LIBRARY_PATH` 必须启动前生效）。
或直接 `sudo apt install libxcb-cursor0`。

### 4.3 雷达不居中 / `'list' object is not callable`

**现象 A**：非正方形窗口里雷达偏左。

**根因**：圆心用了"正方形边长"而不是各自宽高的一半。

**修法**：`cx, cy = w / 2, h / 2`。

**现象 B**：`TypeError: 'list' object is not callable`

**根因**：`self._samples`（数据）与 `self.samples()`（方法）**同名互相覆盖**。

**修法**：内部字段加下划线前缀。

**这两个都是靠"离屏渲染 + 像素检查"发现的**，不是靠肉眼看。

## 五、大模型

### 5.1 回答时有时无

**根因**：`deepseek-v4-flash` 是**推理模型**，`max_tokens` 是"思维链 + 正式回答"之和。
原设 200 → 复杂问题思维链吃光额度 → `content` 为空。

**修法**：`MAX_TOKENS = 2048`。详见 06 篇第 4 节。

### 5.2 `NameError: make_coffee is not defined`

**根因**：`COMMANDS` 列表定义在动作函数**之前**，模块导入时求值就炸了。

**修法**：把 `COMMANDS` 移到所有动作函数定义之后。

### 5.3 `global COFFEE_SCRIPT` 语法错误

**根因**：在模块作用域用 `global` 声明（非法的）。

**修法**：删掉 `global`，只在函数内赋值时用。

## 六、咖啡任务

### 6.1 说 `d` 键不存在

**现象**：以为"按 d 结束"。

**真相**：lerobot 只有 `n` / `r` / `q` 三个键
（`/home/kf/LX/pai0/lerobot/src/lerobot/utils/keyboard_input.py`）：

| 键 | 含义 |
|---|---|
| `n` / `→` | 提前结束 episode 并**正常收尾保存** |
| `r` / `←` | 重录上一集 |
| `q` / `ESC` | 停止整个录制 |

而且是 **pynput 全局监听**，别的窗口敲到也会被当成控制键。

### 6.2 无法判断"咖啡做好了"

**根因**：推理脚本只能靠 `EPISODE_TIME` 走完或被按键结束，**没有画面判断能力**，
ACT 会一直推理下去。

**修法**：最终改成"完全撒手"——把控制权交回给人，用脚本自带的按键交互。
详见 05 篇第 3 节。

## 八、三条通用教训

1. **保留原始错误输出**。`rc=183` 让我们瞎猜了很久，一行 stderr 就定位了。
2. **后台线程顶层必须宽捕获**。`termios.error` 不是 `OSError`，一次漏捕就让链路静默死亡。
3. **别靠"看起来对"下结论**。雷达居中、锁粒度、返回码检查，全靠实测/像素检查/桩脚本验证才发现问题。
