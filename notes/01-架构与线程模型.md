# 01 - 架构与线程模型

## 1. 整体数据流

```
┌──────────────────────────────────────────────────────────────┐
│ M260C 音箱（板内唤醒引擎，唤醒词「你好宽宽」跑在音箱固件里）        │
└───────────────────────────┬──────────────────────────────────┘
                            │ USB 串口 /dev/ttyACM2 (CH9102, 115200)
                            │ 0xA5 帧：握手 0x01 / 设备事件 0x04
                            ▼
              ┌─────────────────────────────┐
              │ serial_reader 线程            │  持续 ACK 握手 + 解析事件
              │  - 节流回 0xFF 确认（1s/次）    │  掉线自动重连
              │  - 提取唤醒 + 声源角度/波束/得分 │
              │  - 30s 一次诊断汇总            │
              └──────────────┬──────────────┘
                             │ _wake_q.put((angle, beam, score))
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ run_live 主循环（业务线程）                                      │
│                                                                │
│  _wake_q.get(timeout=0.5)                                      │
│      ↓ 取到唤醒                                                 │
│  _busy.set()   ← 进入"录音/识别/执行"，期间新唤醒明确忽略           │
│      ↓                                                         │
│  stream_recognize()                                            │
│      ├─ AudioCapture.grab_stream(3s)  先吐 1.2s 预滚再接实时       │
│      ├─ 落盘 audio/cmd_YYYYmmdd_HHMMSS.wav                     │
│      ├─ SenseVoice 滚动重解码线程（每 0.5s 重解整段 → 实时文本）     │
│      └─ 结束后用完整音频定稿                                      │
│      ↓ 得到 text                                                │
│  dispatch(text)                                                │
│      ├─ 命中命令词 → 执行动作（图片 / 咖啡）                       │
│      └─ 未命中 → ask_llm_and_speak()（DeepSeek 问答 + 播报）       │
│                 └─ 再失败 → 播兜底语「暂时还处理不了」              │
│      ↓                                                         │
│  _busy.clear()   ← 回到监听                                      │
└──────────────────────────────────────────────────────────────┘

                    ┌────────────────────────────────────┐
                    │ AudioCapture 采集线程（常开，独立）    │
                    │  arecord → 4000B 块 → 环形缓冲        │
                    │  on_chunk 回调 → HUD 波形/瀑布图       │
                    └────────────────────────────────────┘
```

## 2. 线程清单

| 线程 | 谁创建 | 职责 | 生命周期 |
|---|---|---|---|
| **主线程** | — | `main()` 解析参数、加载模型；`--ui` 时跑 Qt `app.exec()`；否则直接跑 `run_live` | 全程 |
| **serial_reader** | `run_live` | 串口读写、握手确认、唤醒事件入队、诊断统计 | daemon，随进程结束 |
| **audio-capture** | `AudioCapture.start()` | 持续读 `arecord` 输出 → 环形缓冲 → `on_chunk` 回调 | daemon，启动到 `stop()` |
| **worker**（仅 `--ui`） | `run_with_ui` | 跑 `run_live` 主循环，与 Qt 主线程解耦 | daemon |
| **live-decode**（滚动重解码） | `stream_recognize` | 每 0.5s 把当前整段 PCM 重解一次，出实时文本 | 每次识别临时创建 |
| **coffee** | `make_coffee` | 拉起 gnome-terminal 跑机械臂脚本并等它关窗 | daemon |
| **TTS 线程** | `tts_speak_async` | 后台合成+播报（不阻塞调用方） | daemon，一次性 |
| **预热线程** | `main` | 启动时把常用提示音合成进缓存 | daemon，一次性 |

**为什么串口要独立线程**：录音/识别那几秒如果没人应答握手，链路就进入"盲区"（设备可能重发或超时）；独立线程保证握手持续、唤醒事件不丢。

## 3. 共享状态与同步

| 名称 | 类型 | 用途 |
|---|---|---|
| `_wake_q` | `queue.Queue` | 串口线程 → 业务线程传递唤醒事件（线程安全） |
| `_busy` | `threading.Event` | 标记"正在录音/识别/执行"，串口线程据此忽略中途唤醒 |
| `_stop` | `threading.Event` | 全局退出信号（界面关窗 / Ctrl+C / 引擎关闭） |
| `_coffee` + `_coffee_lock` | dict + Lock | 记录咖啡脚本进程，用于**防止重复启动** |
| `_stats` | dict | 诊断计数（握手/事件/唤醒/重复忽略/忙碌忽略/其它），仅串口线程写 |
| `_play_lock`（在 `tts.py`） | `threading.Lock` | **只串行化播放**；合成允许并行 |
| `_tts_speak` | 函数引用 | TTS 函数的懒加载缓存 |

### 关键：播放锁为什么只锁播放

早期版本在调用层用一把大锁把「合成 + 播放」整个串起来，导致必须等
"我想想"整段播完，才开始合成 DeepSeek 的回复，白等 2 秒多。

现在锁只包 `_play()`：
- **合成可以并行** → 第 2 段的合成与第 1 段的播放重叠
- **播放仍互斥** → 两段语音绝不会同时念出来

实测两段播报从 4.0s 降到 3.0s。

## 4. 唤醒事件处理链（为什么"喊了没反应"）

事件从串口到执行，要过 4 道闸门：

```
0x04 设备事件
   │
   ├─① 是唤醒吗？  has_key(obj,"ivw") 或解析到角度
   │     否 → 打印 [设备事件] 诊断信息后丢弃（如开机 started / 版本上报）
   │
   ├─② 是固件重发吗？ 按 start_ms 去重，30s 内同一时间戳只认一次
   │     是 → [状态] 忽略重复唤醒事件(固件重发)
   │
   ├─③ 正在忙吗？  _busy 是否置位
   │     是 → [状态] 识别中又听到唤醒, 本次忽略
   │
   └─④ 通过 → 入队 _wake_q
```

**判断"是不是板子没听到"**：看 `[诊断]` 行里的 `设备事件` 与 `唤醒` 计数。
- `设备事件 0` → 板子根本没上报，是唤醒词/阈值/麦克风的问题
- `设备事件 >0` 但 `唤醒 0` → 事件上报了但没识别成唤醒
- `重复忽略` 高 → 固件在重发同一个唤醒（正常现象，已被去重）

## 5. 启动与关闭流程

### 启动（`main()`）

```
解析参数（--ui / --asr / --no-llm / --duration / --coffee-script ...）
   ↓
a.llm = not a.no_llm            # 大模型兜底默认开
   ↓
--log-file 时打开日志文件
   ↓
--ui 时先做 _ensure_qt_libs()   # 必须在加载模型之前，否则 Qt 兜底重启会让模型加载两次
   ↓
--asr sv 时加载 SenseVoice（约 5~6s，加载一次全程复用）
   ↓
后台线程预热提示音（兜底语 + "我想想"）
   ↓
--wav ?  → 识别该文件后退出
--ui   ?  → run_with_ui()：worker 线程跑 run_live，主线程跑 Qt
否则    → run_live()
```

`run_live` 里再：
1. `AudioCapture(...).start()` 启动常开录音
2. 启动 `serial_reader` 线程
3. 进入 `while not _stop.is_set()` 主循环

### 关闭

| 触发 | 路径 |
|---|---|
| Qt 界面关窗 | `_ui.on_close(lambda: _stop.set())` → 主循环退出 → `_capture.stop()` |
| 终端 Ctrl+C | `KeyboardInterrupt` → `_stop.set()` |
| 子进程异常 | 采集线程 2s 后自动重启 `arecord`；串口线程 3s 后重连 |

## 6. 几个刻意的设计取舍

1. **唤醒词跑在音箱固件里**，不是 PC 上。PC 只收"已唤醒 + 声源角度"事件，
   所以不占 CPU、也不需要常驻的 KWS 模型。
2. **录音常开**（而不是唤醒后再开）。
   代价是持续占用一个 `arecord` 进程，收益是彻底解决首字被切（见 03 篇）。
3. **识别用"滚动重解码"近似流式**。SenseVoice 本身是非流式的，
   每 0.5s 把已录到的**整段**重解一次，得到逐步变长的实时文本；结束时用完整音频定稿。
4. **命令词匹配用"包含"而非"等于"**。因为识别结果常带唤醒词（"你好宽宽打开图片"），
   包含匹配能直接命中。
5. **大模型只做问答，不下发动作**。reply 仅用于播报，没有任何执行路径（安全考虑）。
